ExpenseTrack Pro Architecture
ExpenseTrack ProEngineering atlas

How the ledger is built, end to end

A household expense tracker for Indian families, shared by the whole household. A React app on S3 and CloudFront calls a FastAPI app on Lambda through API Gateway. Cognito handles sign-in, DynamoDB stores each household's ledger, and a scheduled Lambda logs recurring bills and builds budget emails. The infrastructure is AWS CDK in Python. This page is the visual companion to the repository README.

Design decisions

Compute

One Lambda for the whole API

Routing happens inside FastAPI. Two more functions do background work: scheduled jobs, and migrations after each deploy.

Auth

Tokens at the gateway, roles in the app

The JWT authorizer rejects bad tokens before Lambda runs. Each route then checks the caller is a member of the household with the role it needs.

Storage

One table, keyed by household

Each household is one partition, LEDGER#<id>. Two sparse indexes cover memberships, invites, due bills and date ranges. No scans on requests.

Files

Receipts skip Lambda

The browser uploads and downloads directly from S3 with 5-minute presigned URLs scoped to the household.

Secrets

Not in git, not in templates

CDK emits {{resolve:secretsmanager:…}} references. CloudFormation fills them in at deploy time.

Schema

Data changes ship as code

Numbered migrations run once per table after each deploy. They only write what's missing, so a re-run never overwrites users' changes.

Life of a request

What happens between a click and a DynamoDB read. Steps 3 and 5 are the security gates: the gateway checks the token, the app checks the household membership.

1

Get a token

Amplify returns the Cognito ID token, refreshing it if needed.

fetchAuthSession()
2

Call the API

Sends Authorization: Bearer and X-Ledger-Id.

services/cloudApi.ts
3

Gateway verifies

Signature, issuer = user pool, audience = app client. Fail → 401.

HTTP API JWT authorizer
4

Who is it?

Mangum hands off to FastAPI; the verified sub, email and email-verified claims identify the caller.

dependencies/auth.py
5

Member? Then read

One GetItem on MEMBER#<sub> checks the role, then the router queries LEDGER#<id>.

dependencies/ledger.py → db.py

Why the ID token and not the access token? The HTTP API authorizer checks aud against the app client id, and only Cognito's ID token carries aud.

Signature check

HMAC-SHA1(authToken, fullUrl + key+value of every form field, sorted), base64-encoded, compared in constant time with X-Twilio-Signature.

Message parsing

The first number is the amount (it may start with ₹, rs or inr). The rest is the description. A keyword table picks the category: auto → auto_rickshaw, petrol → fuel, dinner → dine_out, otherwise other.

No scans in request paths; the only scan was the one-off v1 → v2 copy. Only items that need a lookup carry index attributes, so each item costs at most two extra index writes.

Writes

Concurrency

Change fields, not items

db.update_fields sets or removes single attributes and fails if the item is gone, so two people editing at once don't undo each other.

Idempotency

Repeat-safe by key

Recurring expenses use ids like r-<rule>-<date> with put-if-absent; email markers work the same way.

Bulk

Batches for imports

POST /expenses/batch (100) and /batch-delete (500) use BatchWriteItem; multi-item changes like an ownership handover use a transaction.

Migrations

cdk deploy Api→ CDK Trigger→ migrate Lambda→ run migrations not in SYSTEM / MIGRATION#*→ record each one

Each migration is a numbered module in backend/api/migrations/ with an ID and a run(). A failed one isn't recorded and fails the deploy, so it runs again next time. Migrations only write items that are absent, so a re-run never overwrites changes users made in the meantime. Additive changes (a new optional field) need no migration. A change to the key design gets a new table, as v1 → v2 did; the old table is retained, so rolling back means pointing TABLE_NAME at it.

Why one table

Scaling · a strength

Capacity grows by partition

DynamoDB scales per partition key, not per table, so more tables would add no capacity. Each household is a small, separate partition; a million families is a million small partitions. One table also keeps transactions across entity types, permissions, backups and alarms in one place.

Querying · the trade-off

Planned questions only

Every screen asks "this household, maybe a date range", which the keys answer in one partition read. Unplanned questions, such as spend across all households, need a new index or a scan, and there is no server-side SUM or GROUP BY; totals are computed in the browser.

If the product needsUse
Analytics or ad-hoc SQL over all dataKeep DynamoDB for the app; add DynamoDB export to S3 and query it with Athena
Server-side reporting, rich filters, full-text searchPostgreSQL (RDS or Aurora), at the cost of sizing, patching and Lambda connection handling
NeitherStay as is

§12

Local development

Needs Node.js 20+, Python 3.12+, and the AWS CLI v2 for deploys. Pick the mode that matches the work.

The deployed API and Cognito already allow http://localhost:5173, so no backend setup is needed. You sign in with a real account and read and write real dev data.

cd frontend
npm install
npm run dev:aws        # http://localhost:5173/ — root path matches the Cognito callback URLs

Use dev:aws, not dev. Plain dev serves under /ExpenseTrack-Pro/, so a Google or Facebook redirect back to localhost:5173/ misses the app.

FastAPI under uvicorn against a local DynamoDB. boto3 honours AWS_ENDPOINT_URL_DYNAMODB, so no code changes are needed.

# 1) local DynamoDB (or: pip install "moto[server]" && moto_server -p 8001)
docker run -d -p 8001:8000 amazon/dynamodb-local

# 2) fake credentials, point boto3 at it
export AWS_ACCESS_KEY_ID=local AWS_SECRET_ACCESS_KEY=local AWS_DEFAULT_REGION=ap-southeast-2
export AWS_ENDPOINT_URL_DYNAMODB=http://localhost:8001

# 3) same keys and indexes as the CDK table
aws dynamodb create-table --endpoint-url http://localhost:8001 \
  --table-name expense-track-pro-local \
  --attribute-definitions AttributeName=PK,AttributeType=S AttributeName=SK,AttributeType=S \
    AttributeName=GSI1PK,AttributeType=S AttributeName=GSI1SK,AttributeType=S \
    AttributeName=GSI2PK,AttributeType=S AttributeName=GSI2SK,AttributeType=S \
  --key-schema AttributeName=PK,KeyType=HASH AttributeName=SK,KeyType=RANGE \
  --global-secondary-indexes \
    'IndexName=GSI1,KeySchema=[{AttributeName=GSI1PK,KeyType=HASH},{AttributeName=GSI1SK,KeyType=RANGE}],Projection={ProjectionType=ALL}' \
    'IndexName=GSI2,KeySchema=[{AttributeName=GSI2PK,KeyType=HASH},{AttributeName=GSI2SK,KeyType=RANGE}],Projection={ProjectionType=ALL}' \
  --billing-mode PAY_PER_REQUEST

§13

Test & deploy

A pytest suite covers the backend. Deploys are CDK change sets; a failed stack update, including a failed migration, rolls back automatically.

Routine frontend release

npm run build:aws→ frontend/dist-aws→ cdk diff→ cdk deploy ExpenseTrack-Frontend-dev --exclusively→ S3 sync + CloudFront /* invalidation

Watch for replacements in Auth and Data. A new user pool means every user signs up again; a replaced table loses its data outside prod. If cdk diff shows [-]/[+] with “replace”, stop and rethink. Removing an output another stack imports also fails the deploy; the v1 table's exports survived the switch because the Api stack still reads that table for migrations.

First-time setup

  1. AWS access

    aws login --region ap-southeast-2, or an IAM key limited to sts:AssumeRole on cdk-hnb659fds-* plus secretsmanager:*Secret* on expense-track-pro/*. Check with aws sts get-caller-identity.

  2. Install tools

    npm i -g aws-cdk, then a venv in backend/cdk with pip install -r requirements.txt.

  3. Bootstrap CDK

    cdk bootstrap aws://<account>/ap-southeast-2, once per account and Region.

  4. Create the three secrets

    The Auth and Api stacks fail to deploy without them (see §11).

  5. Build the frontend

    cd frontend && npm ci && npm run build:aws. The Frontend stack uploads dist-aws.

  6. Deploy everything

    cdk deploy --all for dev, or add -c stage=prod for a separate prod copy.

  7. Wire up the outputs

    For a new pool or API, update amplify.ts, API_BASE_URL and the origin lists, then redeploy the Frontend stack.

  8. External consoles

    Add the /oauth2/idpresponse URL in Google and Facebook, add the Facebook email permission, set the Twilio webhook.

  9. Confirm the SNS subscription

    Click the link in AWS's email, or alarms are never delivered.

§14

Monitoring

Five alarms on SNS topic expense-track-pro-alerts-<stage>, delivered by email. Missing data counts as not breaching, so quiet periods stay quiet.

LambdaErrorsAlarmLambda Errors · Sum over 5 min≥ 1
LambdaThrottlesAlarmLambda Throttles · Sum over 5 min≥ 1
ApiServerErrorAlarmHTTP API 5xx · Sum over 5 min≥ 1
ApiHighLatencyAlarmHTTP API Latency · p99 over 5 min≥ 3000 ms × 2
TableThrottledRequestsAlarmDynamoDB throttled requests · Sum over 5 min≥ 1
aws logs tail /aws/lambda/<ApiFunctionName> --follow --region ap-southeast-2       # FastAPI tracebacks for any 500
aws logs tail /aws/lambda/<JobsFunctionName> --since 1d --region ap-southeast-2     # recurring, alerts, summary runs
aws logs tail /aws/lambda/<MigrateFunctionName> --since 1d --region ap-southeast-2  # migration counts per deploy

Cost

Everything is pay-per-use, so an idle stage costs close to nothing. Watch Secrets Manager (about $0.40 per secret per month), Cognito MAUs past the free tier, point-in-time recovery storage, SES once sending, and Twilio once off the trial.

Account constraints

Regional resources must be in ap-southeast-2: no Lambda@Edge, StackSets or cross-Region replication. Sudden AccessDenied usually means the project's spend limit was hit.

§16

Known limits & tech debt

What to fix before a real launch.

  • Backend tests exist; no frontend tests and no CI yet.
  • Old TypeScript and ESLint errors in older files; npm run build fails, build:aws skips the type check.
  • Pool ids and API URL are hard-coded instead of injected per stage with import.meta.env.
  • Cognito's default sender is capped at 50 emails a day; move to SES.
  • Tokens live in localStorage. Consider cookie storage, shorter lifetimes and refresh-token rotation.
  • The app loads a household's whole expense list, and the jobs walk one LEDGERS index key; both have planned fixes (§8).
  • No server-side aggregation or ad-hoc querying; add DynamoDB export to S3 and Athena if analytics are needed.
  • The schema-v1 table is retained; remove it and LEGACY_TABLE_NAME once v2 is verified everywhere.
  • Emails are built but not sent until a domain is verified in SES; invites are in-app only until then.
  • Offline mode queues new expenses only; edits need a connection.
  • Deleting a household leaves its receipt photos in S3.
  • Receipt uploads aren't size-limited or checked after upload.
  • WhatsApp runs on Twilio's trial sender (5 numbers), and the real Auth Token isn't stored yet.
  • No custom domain; the site uses the CloudFront default.
  • Old GitHub Pages scripts and the /ExpenseTrack-Pro/ base path still exist.
